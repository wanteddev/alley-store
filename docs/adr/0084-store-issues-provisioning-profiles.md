# ADR-0084: 프로비저닝 프로필은 스토어가 발급해 보관하고, 워커가 서명 직전에 넣는다

- 상태: 수락됨
- 날짜: 2026-11-23

## 맥락

iCloud, Push, Associated Domains, Network Extension 같은 restricted entitlement 를 쓰는
앱은 번들 안에 `Contents/embedded.provisionprofile` 이 있어야 합니다. 없으면 서명과 공증은
통과하는데 실행할 때 macOS 가 앱을 멈춥니다(설계 문서 2장).

지금까지는 **개발자가 그 파일을 직접 넣어 올려야** 했습니다. 워커는 프로필이 있는지만 보고
통과시켰습니다(`Entitlements.validate`). 조직 Apple 계정에 접근할 수 없는 사람은 그런 앱을
올리는 순간 막혔고, 접근할 수 있는 사람도 Xcode 가 자기 맥의 인증서로 만든 프로필을 넣어
왔습니다. 그 프로필에 워커의 인증서가 없으면 실행할 때 거절됩니다.

스토어의 ASC 연동은 인증서 조회, App ID 조회, App ID 등록 셋뿐이었습니다. capability 를
켜지도 프로필을 만들지도 못했고, 워커(`SigningPipeline`)에는 프로필이라는 개념이 없었습니다.

구현하면서 Apple 문서로 확인한 사실이 결정에 영향을 줬습니다.

- capability 를 켜면 그 App ID 로 만든 기존 프로필을 Apple 이 무효로 만든다. 프로필은
  고칠 수 없고(`PATCH` 없음) 지우고 새로 만들어야 한다
- 프로필에 든 인증서로 서명하지 않으면 실행할 때 거절된다. 프로필에 앱 신원
  (`com.apple.application-identifier`)이 서명에도 실려 있어야 macOS 가 그 프로필이 이 앱
  것인지 확인한다
- iCloud 컨테이너, App Group, Apple Pay 판매자 ID 를 App ID 에 연결하는 API 는 없다
- Sign in with Apple, WeatherKit 등은 Developer ID 배포에서 아예 쓸 수 없다
- 2017년 이후 발급한 Developer ID 프로필은 18년짜리다. 계획 문서가 적은 "1년" 은 틀렸다
- 프로필을 만들려면 팀 키여야 하고 역할이 Admin 이어야 한다. 개인 키는 이 엔드포인트를
  못 쓴다

## 결정

### 서버가 발급해 보관하고, 지시서에 실어 보낸다

서버가 ASC 로 프로필을 만들어 앱마다 하나씩 보관합니다(`provisioning_profiles`). 서명 잡
지시서(`SigningJobDTO.provisioningProfile`)에 실어 보내면 워커가 번들에 넣고 서명합니다.

**서명 키는 여전히 워커에만 있습니다(ADR-0002).** 프로필은 인증서의 공개 부분과 허용 권한을
Apple 이 서명해 둔 파일이라 비밀이 아니고, 그것만으로는 아무것도 서명할 수 없습니다.

### 사람이 누를 때만, 버튼 하나로 끝까지

앱 소유자나 관리자가 앱 상세의 "프로비저닝 프로필" 구역에서 누르거나, 프로필 때문에 멈춘
버전 옆의 "프로필 발급하고 다시 시도" 를 누릅니다. 한 번 누르면

1. App ID 가 없으면 이 앱의 번들 ID 로 만들고
2. 모자란 capability 를 켜고
3. 살아 있는 Developer ID Application 인증서를 **전부** 넣어 프로필을 만들고
4. 보관한 뒤 Apple 쪽 옛 프로필을 지웁니다

실패 옆 버튼은 여기에 더해 그 버전을 다시 큐에 넣습니다. **Apple 화면에서 먼저 할 일이
남으면 넣지 않습니다.** 컨테이너를 연결하지 않았거나 대응표에 없는 capability 가 빠졌으면
다시 시도해도 워커에서 또 멈추기 때문입니다. 그때는 할 일을 화면에 띄우고 멈춥니다.

구역은 프로필이 필요한 권한이 보이거나 발급한 것이 있을 때만 나옵니다. 권한은 **가장 최근
버전의** 업로더가 준 entitlements 와, 워커가 서명을 멈추며 보고한 키
(`SigningJobUpdate.profileEntitlements`)를 합쳐 판단합니다. 옛 버전까지 합치면 예전에
넣었다 뺀 권한이 발급을 막습니다. 실패 옆 버튼은 그 버전의 권한으로 발급합니다. 이미 서명된 번들의 권한은 워커만 읽을 수 있어서 뒤쪽이 없으면 그런 앱에는
자리가 영영 나오지 않습니다.

### App ID 는 앱마다 따로 쓴다

스토어가 발급하는 프로필은 앱의 explicit App ID 로만 만듭니다. ADR-0005 의 가운데 칸
("프로필은 필요하나 특수 capability 없음 → 와일드카드 공유")은 쓰지 않습니다. 실제로 프로필이
필요한 앱은 거의 다 capability 가 필요하고, 와일드카드 App ID 에는 그것을 켤 수 없습니다.

### capability 는 대응표에 있는 것만 켠다

권한 키와 capability 의 대응은 Apple 이 표로 내놓지 않아서 이름을 맞춰 표로 만들었습니다
(`ProfileCapability`). 표에 있는 것은 켜고, 나머지는 이렇게 다룹니다.

| 경우 | 다루는 법 |
| --- | --- |
| 켰지만 식별자를 연결해야 함 (iCloud 컨테이너, Apple Pay 판매자 ID) | 켜기까지 하고, 어느 화면에서 무엇을 하고 다시 발급하라고 말한다 |
| 대응표에 없음 | 프로필은 만들고, 만든 프로필이 그 키를 허용하는지 보고 말한다 |
| 모든 프로필에 실림 (`keychain-access-groups`, 앱 신원 두 줄) | 켤 것 없이 만든다 |
| Developer ID 가 못 씀 | 발급하지 않고 권한을 빼라고 말한다. Apple 에 아무것도 만들지 않는다 |

### 워커는 스토어 프로필로 덮어쓰고, 서명 전에 대조한다

- 지시서에 프로필이 있으면 번들에 있던 것을 **덮어씁니다.** 덮어썼다는 사실은 잡 로그에
  남깁니다
- 서명 전에 entitlements 와 프로필이 허용하는 권한을 대조합니다. 키가 있는지 보고, 양쪽
  값이 문자열이면 선언한 값이 프로필 값(끝의 `*` 와일드카드 포함)에 드는지까지 봅니다.
  컨테이너를 연결하지 않은 프로필은 키는 있고 값이 비어 있어서, 키만 보면 통과하고 실행할
  때 죽습니다. 어긋나면 무엇이 모자란지 말하며 멈춥니다. 개발자가 넣어 온 프로필도 똑같이
  대조합니다
- 바깥 `.app` 의 서명에 실리는 앱 신원 두 줄(`com.apple.application-identifier`,
  `com.apple.developer.team-identifier`)을 **프로필 값으로 덮어씁니다.** 다른 팀으로
  서명됐던 빌드에는 옛 팀의 값이 남아 있고, 그대로 두면 실행할 때 죽습니다
- 업로더 plist 를 안쪽 헬퍼 `.app` 에 붙일 때, 헬퍼에 자기 프로필이 없으면 프로필이 필요한
  권한을 뺍니다. 그대로 두면 헬퍼가 뜨자마자 죽습니다. 자기 프로필이 있으면 신원을 그
  프로필 값으로 맞춥니다
- 번들과 `Contents` 가 심볼릭 링크면 프로필을 넣지 않고 멈춥니다. 올린 zip 은 링크를 그대로
  풀어 놓아서, 따라가면 작업 디렉터리 밖의 파일을 덮어씁니다
- 값이 어긋나 멈추면 실패 사유에 선언한 값과 프로필이 허용하는 값을 함께 적습니다. Apple
  쪽에서 컨테이너를 연결하면 풀리는지, 앱이 다른 팀의 값을 적었는지는 값을 봐야 가릅니다

### 번들 ID 가 임시값이면 프로필 실패에서 확정한다

dmg 로 올린 앱은 번들 ID 가 임시값으로 시작하고, 서명이 끝나야 확정됩니다(ADR-0034).
그런데 프로필은 확정된 번들 ID 로만 발급됩니다. 프로필이 필요한 앱이 첫 서명에서 멈추면
서명은 프로필을, 프로필은 서명을 기다립니다. 그래서 **프로필 때문에 멈춘 실패에 한해** 워커가
읽은 번들 ID 를 실어 보내고, 서버가 성공 때와 같은 검사(접두사 정책, 중복)를 거쳐 확정합니다.
다른 실패에서는 확정하지 않습니다.

프로필은 CMS 로 감싼 XML plist 인데, 서버가 리눅스라 `security cms` 가 없습니다. 바이트에서
plist 부분을 잘라 읽고(`ProvisioningProfile`), 워커와 서버가 같은 코드를 씁니다.

### 실패 갈래를 하나 더 둔다

프로필이 없거나 모자라 멈추면 `provisioning_profile_required` 로 보고합니다. 예전에는
`entitlements_rejected` 에 함께 들어갔는데, 그 갈래에는 "entitlements 를 붙여 다시 시도"
하는 칸이 따라옵니다(ADR-0036). 프로필이 모자란 사람에게는 헛걸음입니다.

### 프로필이 필요한 권한의 기준을 고친다

`com.apple.developer.` 접두사에 `keychain-access-groups` 와 `com.apple.application-identifier`
를 더했습니다(TN3125). 계획 문서는 "접두사로만 보면 과하게 막는다" 고 걱정했는데, 접두사가
붙은 것 중 프로필 없이 되는 것은 Apple 문서에 없었습니다. 실제 구멍은 반대쪽, 접두사가 없어
놓치던 두 키였습니다.

### 만료일은 적어 두기만 한다

`expires_at` 과 넣은 인증서 ID 를 함께 저장합니다. 지켜보는 것은 만료 감시(#89)에 붙입니다.

## 대안과 기각 사유

**워커가 ASC 에서 직접 받는다** - 워커는 자기가 어느 인증서로 서명하는지 정확히 알아서, 그
인증서 하나만 넣은 프로필을 만들 수 있습니다. 서버에 ASC 쓰기 권한이 필요 없어지기도 합니다.
기각한 이유는 **Admin 역할의 ASC 키가 워커 맥마다 놓이게 되기 때문입니다.** 지금 그 키는
서버 하나에만 있습니다. 워커가 여러 대면 각자 발급해 Apple 계정에 프로필이 대수만큼 쌓이고,
화면은 무엇이 발급됐는지 알 길이 없습니다.

**서명이 프로필 때문에 실패하면 서버가 알아서 발급한다** - 사람 손이 전혀 안 갑니다. 기각한
이유는 ADR-0053 과 같습니다. App ID 와 프로필은 Apple 계정에 남고 지우는 것은 우리 손을
떠납니다. 사람이 모르는 사이에 계정이 바뀌면 안 됩니다.

**App ID, capability, 프로필을 단계별 버튼으로 둔다** - 무엇이 일어나는지 단계마다 분명하고,
실패한 단계만 다시 누르면 됩니다. 기각한 이유는 **capability 를 켜는 순간 기존 프로필이 무효가
되기 때문입니다.** 그 단계에서 멈추면 서명이 오히려 깨집니다. 순서도 사람이 알아야 합니다.

**개발자가 넣은 프로필을 존중한다** - 지금 동작 그대로이고, 개발자가 일부러 넣은 것을 건드리지
않습니다. 기각한 이유는 **그 프로필에 워커의 인증서가 있다는 보장이 없기 때문입니다.** 없으면
공증까지 통과하고 사용자의 맥에서 실행할 때 거절됩니다. 가장 늦게 드러나는 실패입니다.

**와일드카드 App ID 로 발급한다** - 포털 엔트리가 하나로 끝나서 ADR-0005 의 취지에 맞습니다.
기각한 이유는 위에 적은 대로 와일드카드에는 capability 를 켤 수 없어서, 실제로 프로필이 필요한
앱 대부분에 쓸모가 없기 때문입니다.

**키만 대조한다** - 키마다 값 규칙이 달라서(배열의 부분집합, `TEAMID.*` 와일드카드, 문자열
하나) 키만 보면 단순합니다. 처음에는 이렇게 했습니다. 기각한 이유는 리뷰에서 나온 경로
하나 때문입니다. capability 만 켜고 iCloud 컨테이너를 연결하지 않은 프로필은 키는 있고
값이 비어 있습니다. 키만 보면 통과하고, 서명과 공증을 거쳐 사용자의 맥에서 실행할 때
죽습니다. 이 결정이 막으려던 바로 그 실패라서 문자열 값까지 봅니다. 참·거짓이나 사전 같은
값은 여전히 키만 봅니다.

## 결과

**좋은 점**

- 조직 Apple 계정에 접근할 수 없는 개발자도 restricted entitlement 를 쓰는 앱을 올릴 수
  있습니다. 막히면 그 실패 옆에서 앱 소유자가 한 번 누르면 됩니다
- 들어가는 프로필은 늘 워커의 인증서를 담고 있습니다
- 프로필이 허용하지 않는 권한을 서명 전에 이름까지 말해 줍니다. 전에는 사용자의 맥에서
  `Unsatisfied entitlements` 로 죽었습니다
- 접두사가 없어 놓치던 `keychain-access-groups` 를 이제 잡습니다

**나쁜 점**

- **서버의 ASC 키가 Admin 역할이어야 합니다.** 전에는 조회와 App ID 등록만 했습니다. 서버가
  털리면 Apple 계정에 App ID, capability, 프로필을 만들고 지울 수 있습니다. 서명 키는 여전히
  없지만 계정을 어지럽힐 수는 있습니다
- **인증서를 갈면 프로필을 다시 발급해야 합니다.** 프로필은 만들 때의 인증서만 압니다. 지금은
  사람이 알아채야 하고, 감시는 #89 에 붙입니다. 넣은 인증서 ID 를 저장해 둔 것이 그 준비입니다
- 대응표는 Apple 이 공개하지 않은 것을 이름으로 맞춘 것입니다. 틀리면 켜기가 실패하거나
  프로필이 그 키를 허용하지 않고, 사람이 Apple 화면으로 가야 합니다
- iCloud 컨테이너, App Group, 판매자 ID 연결은 여전히 사람 몫입니다. 연결하면 프로필이
  무효가 되므로 다시 발급도 눌러야 합니다
- 문자열이 아닌 값(참·거짓, 사전)이 어긋나는 것은 서명 전에 못 잡습니다
- 서버는 프로필이 허용하는 **키**만 저장합니다. 화면의 "허용하지 않는 권한" 안내는 키
  단위라, 값이 어긋난 것은 워커가 서명을 멈출 때에야 보입니다
- 두 사람이 같은 앱에서 동시에 발급하면 한쪽은 `app_id` 유일 제약에 걸려 실패하고, Apple 에
  프로필이 하나 남습니다. 드문 일이라 잠그지 않았습니다
- 개발자가 넣은 프로필과 앱 신원 값을 말없이 덮어씁니다. 잡 로그에만 남습니다
- 관리자가 아닌 앱 소유자(일반 개발자)도 조직 Apple 계정에 항목을 만들 수 있습니다.
  ADR-0053 의 App ID 만들기와 같은 수준이지만 할 수 있는 일은 더 많습니다
- 헬퍼에서 권한을 빼는 것은 헬퍼가 정말 그 권한을 써야 하는 앱이면 그 기능을 조용히 죽입니다.
  헬퍼에 자기 프로필이 있으면 빼지 않으므로, 그런 앱은 개발자가 헬퍼 프로필을 넣어 와야 합니다
- 임시 번들 ID 가 서명에 성공하지 않은 번들로 확정될 수 있습니다. 그 뒤 다른 번들 ID 로 다시
  올리면 등록값과 달라 막힙니다. 프로필 실패로 멈춘 번들도 정책 검사는 통과한 것이라 받아들였습니다
- macOS 15 부터 `group.` 으로 시작하는 App Group 은 프로필이 있어야 사용자 동의 없이 열립니다.
  App Group 자체는 프로필 없이 서명되므로 여기서는 발급 대상으로 보지 않습니다

**후속**

- 프로필 만료와 인증서 교체 감시 (#89)
- ADR-0053 의 "explicit App ID 는 앱 상세에서 만든다" 버튼은 이 발급 버튼으로 바뀌었습니다.
  와일드카드 부분은 그대로입니다
