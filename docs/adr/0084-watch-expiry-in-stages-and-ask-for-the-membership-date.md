# ADR-0084: 만료는 단계마다 한 번 알리고, 멤버십 만료일은 관리자가 적는다

- 상태: 수락됨
- 날짜: 2026-11-23

## 맥락

앱 서명 화면이 Developer ID 인증서 만료를 30일 전부터 빨갛게 보여줬지만, 그 화면을
여는 사람이 있어야 보였습니다. 주기 작업은 워커 감시·멈춘 잡 회수·draft 청소·토큰
만료 예고·스토어 소식뿐이었고 인증서나 멤버십 만료를 보는 것은 없었습니다 (이슈 #89).

만료되면 앱 하나가 아니라 **모든 앱이 한꺼번에** 서명을 못 합니다. 그런데 지켜볼
것들의 사정이 서로 다릅니다.

- 인증서는 App Store Connect API 가 만료일을 줍니다.
- Apple Developer Program 멤버십은 1년마다 끊기는데 **ASC API 에 만료일이 없습니다.**
- 곧 프로비저닝 프로필도 붙습니다. 1년짜리이고 인증서를 갈면 무효가 됩니다.

그리고 6시간마다 도는 작업이 매번 알리면 30일 전 알림이 하루 네 번씩 한 달 동안
옵니다. 그러면 정작 하루 전 알림을 아무도 안 읽습니다.

## 결정

**만료 감시(`ExpiryWatch`)를 `PeriodicSweep` 하나로 두고, 무엇을 볼지는 감시 대상
(`ExpirySource`)이 정합니다.** 감시는 단계를 세고, 운영 알림으로 보내고, 보낸 것을
적는 일만 합니다.

- **단계마다 한 번 알린다.** 30·14·7·1일 전, 그리고 만료. 처음 볼 때 이미 7일
  남았으면 7일 단계 한 통만 갑니다. 첫 단계는 화면이 빨개지는 날과 같게 묶었습니다
  (`PortalGrouping.expiringSoonDays`).
- **만료됐거나 날짜를 모르면 일주일마다 다시 알린다.** 지나가는 단계와 달리 머무는
  동안 계속 문제라서입니다.
- **알린 것은 표(`expiry_notices`)에 적는다.** 만료 시각이 바뀌면(갱신했거나 날짜를
  고쳐 적었으면) 다른 것으로 보고 처음부터 셉니다. 멀어지면 기록을 지웁니다.
- **실제로 보낸 것만 적는다.** 운영 알림이 아무 데도 닿지 않았으면 기록하지 않고
  다음 주기에 다시 봅니다. 이를 위해 `Notifier.notifyOperators` 가 보냈는지를 돌려주게
  했습니다.
- **멤버십 만료일은 관리자가 앱 서명 화면에 적는다.** 날짜(`2027-03-15`)로 저장하고
  그날 0시를 만료로 봅니다. 남은 날은 화면과 같이 날짜끼리 셉니다. 시각으로 세면
  화면은 "31일 남음" 인데 알림은 "30일 뒤" 가 됩니다. **비어 있으면 적을 때까지 일주일마다 적어 달라고 알린다.**
  끄는 자리는 두지 않습니다. 멤버십 없이 쓰는 스토어는 없습니다.
- **ASC 를 하루 넘게 못 읽으면 한 번 알린다.** 다시 읽히면 잊고 다음 실패를 처음부터
  셉니다. API 키 폐기나 멤버십 단절을 날짜와 별개로 잡는 마지막 그물입니다.

6시간마다 돌고, 첫 실행은 기동 10분 뒤입니다. 첫 주기를 다 기다리면 그보다 자주
배포하는 주에는 한 번도 돌지 못합니다.

새로 지켜볼 것이 생기면 `ExpirySource` 하나와 `ExpiryKind` 케이스 하나를 더합니다.
`ExpiryKind` 의 문구 switch 가 컴파일을 막아, 문구 없이 알림이 나가지 않습니다.

## 대안과 기각 사유

**멤버십을 인증서 만료로 갈음하기.** 적을 칸도 사람의 손도 필요 없고, 이미 읽는
값만으로 끝납니다. 하지만 인증서는 5년, 멤버십은 1년이라 인증서 만료일로는 멤버십이
끊기는 해를 거의 잡지 못합니다. 사실상 멤버십을 보지 않는 것과 같습니다.

**멤버십은 ASC 읽기 실패로만 알기.** 역시 사람이 적을 것이 없고, 멤버십이 끊기면
ASC 도 거절할 가능성이 큽니다(확인하지는 못했습니다). 하지만 끊긴 **뒤에** 알게 됩니다. 그때는 이미
서명과 공증이 막혀 있습니다. 미리 알리려는 이 작업의 목적과 맞지 않아 그물로만
남겼습니다.

**쓸 때마다 알리기 (기록 없이).** 표가 필요 없고 가장 단순합니다. 서버가 다시 떠도
상태가 꼬일 일이 없습니다. 하지만 6시간 주기라 30일 전부터 하루 네 번씩 옵니다.
토큰 만료 예고(`UserTokenExpiryNotice`)도 같은 이유로 한 번만 보내게 했습니다.

**기록을 메모리에 두기.** 표와 마이그레이션이 필요 없습니다. 하지만 배포할 때마다
기억이 지워져, 배포가 잦은 주에는 같은 단계를 여러 번 받습니다. "하루 넘게 실패" 도
재시작하면 처음부터 세어 영영 하루를 못 채울 수 있습니다.

**대상마다 감시 작업을 따로 두기.** 인증서 감시, 멤버십 감시, 프로필 감시를 각자
`PeriodicSweep` 으로 두면 서로 독립적이고 하나가 다른 것을 막지 않습니다. 하지만 단계·
반복·기록 규칙을 셋이 각자 갖게 되고, 하나만 고치면 알림 리듬이 갈라집니다. 읽는
쪽만 나누고 세는 쪽은 하나로 두었습니다.

## 결과

**좋은 점.** 인증서와 멤버십 만료를 화면을 열지 않아도 압니다. 단계마다 한 번이라
알림이 소음이 되지 않습니다. 프로필 같은 새 대상은 읽는 쪽만 더하면 같은 리듬으로
알립니다.

**나쁜 점.**

- **멤버십은 사람이 적은 날짜만큼만 맞는다.** 갱신하고 고치지 않으면 지난 날짜로 보고
  계속 알립니다. 그 알림이 고치라는 신호이긴 하지만, 사람이 한 번 더 손을 써야 합니다.
- **날짜가 비어 있는 스토어는 배포하자마자 알림을 받는다.** 이미 도는 스토어도 이
  기능이 들어가는 순간부터 일주일마다 받습니다. 의도한 것이지만 첫 알림은 예고 없이
  옵니다.
- **ASC 의 기록과 워커의 실제 인증서가 다를 수 있다.** 스토어는 ASC 가 말하는 것만
  봅니다. 새 인증서를 만들었는데 워커 키체인에 안 넣었으면 알림은 멎었는데 서명은
  실패합니다. 반대로 이미 바꾼 옛 인증서가 ASC 에 남아 있으면 알림이 계속 옵니다.
- **서버가 여러 대면 같은 단계 알림이 겹칠 수 있다.** 두 대가 같은 순간에 같은 행을
  보고 둘 다 보낼 수 있습니다. 토큰 만료 예고와 같은 수준이고, 6시간 주기라 실제로
  겹칠 일은 드뭅니다.
- **ASC 인증서는 200개까지만 읽는다.** 페이지를 넘기지 않아서, 개발 인증서가 아주 많은
  팀에서는 서명용 인증서가 첫 페이지 밖으로 밀려 감시에서 빠질 수 있습니다. 앱 서명
  화면도 같은 한계를 갖고 있습니다.
- **만료 시각을 그날 0시로 본다.** 멤버십을 그날 끝까지 쓸 수 있어도 당일 0시에 "지났다"
  고 알립니다. 늦게 알리는 것보다 하루 일찍 알리는 쪽을 골랐습니다.

**후속 과제.**

- 워커 키체인의 실제 인증서와 ASC 값 대조 (워커가 하트비트로 인증서 정보를 올려야
  해서 워커 릴리스가 따라온다).
- 프로비저닝 프로필 만료를 `ExpirySource` 로 태운다.
